Steerholm is the plane your AI agents work on. Your resources — files,
repositories, databases, internal services — are connected to it, and your agents
act on them only from the plane, under your control and on your rules.

It is one plane with two faces:

- **An action plane for your agents** — where they act on your resources.
- **A control plane for you** — where you decide which agent can reach which
  resource and what it may do there, down to each action and its arguments.

Nothing reaches a resource that you didn't allow.

New here? [Install Steerholm](/getting-started/installation), then the
[quickstart](/getting-started/quickstart) gets you to a scoped agent in minutes.
For the full mental model, see [One plane](/concepts/one-plane).

## Why it exists

Connect an agent to a resource and it can use every tool the resource's MCP server
offers — any file in the folder, any git command on the repository, any query on
the database. There is no way to say
"read the history but don't commit" or "only `SELECT` on this database".

Steerholm puts that decision with you. Your agents work on one plane with your
resources connected to it, and every action an agent takes there is checked
against your rules before it reaches the resource.

## Agents, resources, and grants

<CardGroup cols={3}>
  <Card title="Agents" icon="robot" color="#10b981">
    The AI tools you govern — Claude Code, Cursor, VS Code, OpenCode. Each has a
    name, an access key, and a policy.
  </Card>

  <Card title="Resources" icon="server" color="#10b981">
    Your files, repositories, databases and services — each connected to the plane
    by its **MCP server**, a small connector program that gives agents tools for
    it. Those tools are the actions an agent can take on it.
  </Card>

  <Card title="Grants" icon="key" color="#10b981">
    Your rules for an agent on a resource — which actions, with which arguments.
    No grant means no access.
  </Card>
</CardGroup>

Two things you **add** — agents, and connections to your resources — and the
rules you **grant** between them. See [Permissions](/concepts/permissions) for
the tool and argument syntax.

## Set it up in three moves

<Steps>
  <Step title="Connect a resource">
    A resource is connected to the plane by its MCP server — here, the git MCP
    server for your repositories.

    ```bash
    holm add server git --command "uvx mcp-server-git"
    ```
  </Step>

  <Step title="Add an agent">
    Register an agent and get its access key — the credential it connects with.

    ```bash
    holm add agent coding-agent
    ```
  </Step>

  <Step title="Grant it, on your rules">
    Allow exactly the actions it needs, down to the argument — here, reading
    history, only for repositories under your projects folder.

    ```bash
    holm grant coding-agent git --tool "git_log" --args "repo_path=/home/user/projects/**"
    ```
  </Step>
</Steps>

Then point the agent at `http://127.0.0.1:4767/mcp` with its access key — see
[Add an agent](/guides/add-an-agent). It sees only the tools its policy
allows.
